Pending client updater changes: prepared, NOT deployed

Build-Candidate.ps1 builds and tests a four-component client overlay against the
pinned, signed RC60 client. It never signs, publishes, submits a job, restarts
production or changes server configuration. A new fixture name is required.

Normal flow: Connect checks small signed feeds, downloads only required package
archives, prepares changes, waits for authenticated helper readiness, closes
KSP, applies the changed client files/packages, restarts and consumes the existing
one-shot server/password reconnect intent. No routine approval or restart buttons.
No changes means connect immediately without restarting. Failures stop safely.
If a scene changes before automatic quit, a per-request cancellation marker
prevents the helper applying later when that game process eventually closes.

The authenticated completed receipt binds the game root, selected profile,
installed signed manifest and state-inventory bytes. Subsequent updates reuse
unchanged package inventory without reading every payload. Changed/missing client
files alone enter the replacement/recovery lists. Full archive SHA/RSA/inventory
validation remains. New and changed package bytes remain fully checked.

Full scan remains for first baseline, changed profile, invalid/missing completion
proof, incomplete installation or explicit Verify / repair next connection.
Unchanged managed payload is trusted after completion; arbitrary manual edits
inside unchanged packages need explicit Repair. This is intentional, not an
anticheat/tamper-monitoring mechanism. The signed client ZIP is still downloaded
on a client-version change; transport is not a per-file binary-delta protocol.

Extra profile-excluded mods move to APF/.disabled-mods, with ordinary recovery
records. Saves, identity, controls and runtime settings retain protection.
Windows access-denied errors are not bypassed or auto-approved.
