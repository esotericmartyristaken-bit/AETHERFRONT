Publishing access
Existing GitHub CLI authentication on this server has push access to the
public repository. No further account information is required. If the local
credential is lost, authenticate interactively:

   & "C:\Program Files\GitHub CLI\gh.exe" auth login --hostname github.com --git-protocol https --web

Complete the browser/device-code flow yourself. Do not send your password,
personal access token or device code in chat. The publisher uses the CLI's
local authentication; clients receive no credentials and need no GitHub account.
For a repository-scoped alternative, a fine-grained personal access token
   needs access only to that repository and Contents: Read and write. Metadata
   read access is automatic. Organization approval may be required. Store any
   token locally, never in this project, release assets or client settings.

Publication design
- Immutable package ZIPs live in the non-latest pack-media release.
- Each kesas-rcNN release holds the exact signed APFClientUpdate.json, complete
  client archive and public starter. No game installation, universe, saves,
  player identities, private signing/TLS keys or publish credentials are sent.
- Every Connect fetches GitHub's latest signed feed. The selected server's
  signed active feed prevents early/future-client installation. Invalid
  signatures and wrong hashes are rejected. Approved GitHub redirects require
  valid hostname/chain TLS; the game server retains certificate pinning.
- Public clients use no REST API token. Media caches remain keyed by archive
  SHA256, so changing hosting does not invalidate partial or complete downloads.
- On network/CDN unavailability, the client can resume from the original
  pinned server. Redirect, signature and hash failures never become trusted.

Future release workflow
1. Build a NEW version using the current configured template. Preserve
   universe/configuration/private keys. Re-run release/runtime/upgrade tests.
2. Stage the release archive and queue it through the existing 15-minute bot
   workflow. Existing client and pack transfers must be considered before
   authorizing a restart. The workflow can deploy early on an empty server.
3. Before stopping services, installed hooks verify/upload missing media and
   a draft of the exact native signed feed/client/starter. Existing assets are
   reused only when remote size and SHA256 digest match. Published bytes are
   never clobbered. The first media upload is large and must not compete with
   the protected current transfer; schedule it accordingly.
   Preparation retains its exact native signed archive/feed/starter bytes.
   Never create a version draft from a separately rebuilt candidate ZIP.
   Immediately before stopping, a fresh authoritative bridge snapshot must
   show zero players AND zero connections. Unknown/stale counts fail closed.
4. After server health and the native stable feed are ready, the version release
   becomes GitHub latest. An unknown API outcome is read back before retrying.
   Native activation failures use the existing recovery path. A conflicting
   already-published tag requires a new version, not destructive replacement.
   If GitHub completion becomes uncertain AFTER native activation, do not
   restart or roll back healthy services. Preserve the transaction journal and
   retry the EXACT release archive and notes. Completion-only recovery checks
   native identity/ownership/listeners/signatures before finishing GitHub.
   Completed exact publications are read-only. Newer or conflicting latest
   releases fail closed; uncertain PATCH outcomes receive bounded reads, not
   another PATCH. Use one coordinated publisher: GitHub read/PATCH is not
   atomic against independent simultaneous publishers.
5. New release builds inherit the enabled repository/media settings from the
   current public template unless explicitly overridden. Existing skipped-
   revision clients receive the compatibility update from the original origin
   before using GitHub. Keep that origin available during migration.

Public installation
Download Aetherfront-Starter-kesas-rc22.zip from the kesas-rc22 release, not
the source-code ZIP or pack-media release. Extract into vanilla KSP 1.12.5.
Launch KSP, select Regular or Potato, enter 217.216.49.250 port 18865, Connect.
Bundled trust is retained; no fingerprint entry or GitHub login is required.
The client checks signed updates on every Connect, stages missing content,
then uses the post-exit helper to apply changes and restart. Saves and player
identity are preserved. Changing profiles downloads only the needed delta.

Testing boundaries
Real Unity/Mono verified GitHub TLS, pinned-origin signatures, tamper rejection
and archive/deflate APIs. Full profile-chain verification uses shipped binaries
and the real native helper with a test game placeholder. Headless checks do
not establish UI appearance, rendering, gameplay or representative main-menu
shutdown; final interactive KSP testing is separate.

Source reproducibility
The published full fork predates some historical binary patches. Later overlay
sources and build scripts are included with provenance. Licensed KSP files,
historical binary inputs, runtime state and private keys are excluded. This
snapshot alone is not an exact clean rebuild of every shipping binary.
